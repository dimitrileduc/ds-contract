## D1 — Le modèle de boîte : une règle dans `core/emit-react.ts`, calquée sur `emit-html`

**Décision.** Ajouter dans le CSS Module généré par `core/emit-react.ts` (fonction `generateCss`) la règle que `core/emit-html.ts:131-143` émet déjà, adaptée aux classes de module : pour chaque part racine de premier niveau `r`, `.r, .r *, .r *::before, .r *::after { box-sizing: border-box }`, émise en tête de fichier (même position que dans emit-html). Aucun changement de schéma, aucun changement de contrat.

**Rationale.** Tranché par l'owner le 2026-08-04 (ROADMAP § Prochaines specs, entrée 015 : « un oubli à corriger, pas une limite à nommer »). Le relevé complet est DW-014-002 + reçu `react-box-sizing-absent` : trois surfaces sur quatre sont déjà border-box (Figma via `strokeAlign: INSIDE` ; `emit-html` qui le déclare ; playground `styles.css:51` + canvas-preview `:591`) — seule la bibliothèque livrée compte bordures et padding EN PLUS de la taille posée. Le commentaire d'`emit-html` porte déjà le reçu du bug évité (Switch 36×24 contre 32×20 chez Figma).

**Conséquences mesurées d'avance.**
- Rayon d'impact : **9 contrats** (critère du reçu : une part portant à la fois `width|height|min-width|min-height` ET un padding, dans `tokens` ou `literals`) — accordion-row, carte, coordonnees, faq, footer, google-reviews, review-card, sav, textarea. Re-mesure obligatoire des 9 ; tout chiffre qui bouge est attribué à la cause « unification du modèle de boîte » au registre (FR-004, SC-003) ; un chiffre qui bouge HORS des 9 suspend la publication (FR-011).
- Les 34 fichiers `.module.css` changent d'octets (la règle s'ajoute partout) mais seuls les 9 changent de rendu — c'est le registre avant/après qui le prouve, pas une affirmation.
- Re-pins : `evals/golden.json`, `figma-sync/plugin/engine.receipt.json`, `examples/polaris/figma/*.figma.js` (3 reçus distincts — mémo `emetteur-repin-polaris-showcase`).

**Alternatives rejetées.** (a) Poser la règle globalement dans `src/styles/tokens.css` — rejetée : la sortie emit-react doit être autosuffisante comme celle d'emit-html (le composant consommé seul chez un client doit porter sa règle) ; (b) déclarer une limite nommée — rejetée par l'arbitrage owner du 2026-08-04.

## D2 — L'ordre du chantier : boîte d'abord, conversions ensuite

**Décision.** Aucune conversion littéral→référence ne démarre avant que D1 soit livré ET les 9 contrats re-mesurés/attribués. ## D3 — Granularité du mint : `space.N` pour les espacements, `size.<composant>.*` pour les tailles

**Décision** (tranchée en clarification 2026-08-04, ici opérationnalisée). Espacements (paddings, gaps) → l'échelle générique `space.N` de `tokens/primitives.tokens.json` (idiome 012) ; l'inventaire montre que la plupart existent déjà : `space.{0,4,8,10,12,16,24,32,48,64,89,96,128,392,597}`. Tailles intrinsèques d'une part (width/height/min-width…) → références sémantiques `size.<composant>.<…>` portées par le composant (idiome demo-51 ; précédent vivant : `size.button.icon-only` déjà dans les primitives Piqueray), **obligatoirement** sémantiques dès que la taille varie par variante. Tout mint est from-dump : valeur observée dans le dump/relevé, `$description` citant la provenance, jamais arrondie (« une conversion qui change le rendu n'est pas une conversion »).

**Rationale.** La doctrine est écrite dans le fichier de tokens lui-même (`space.$description` : « minted from-dump so anatomy references tokens, not literals ») et dans la règle geometry-rides-tokens (CLAUDE.md, reçu 013 : 96,91 % → 1,04 % sur un fait invisible). Les 52 contrats archivés demo-51 portent zéro littéral.

## D4 — DW-001, le logo : prop `taille` + référence interpolée, binding Figma `NONE` (limite datée, levée en 016)

**Décision.** `ds.piqueray-logo` reçoit une prop enum `taille` (valeurs nommées d'après les usages relevés dans les dumps header/footer — jamais inventées), et son root remplace `literals: {width: "180px", height: "34px"}` par `tokens: {width: "{size.logo.{taille}.width}", height: "{size.logo.{taille}.height}"}` — l'idiome exact de l'archive (`docs/reference/demo-archive/avatar.contract.json:63-64`, `{size.avatar.{size}}`). `{size.logo.*}` est minté from-dump (aucun token logo n'existe). `ds.header` et `ds.footer` passent `taille` dans `component.props` comme ils passent déjà `couleur`. Version contrat : ajout de prop = **minor** (0.1.0 → 0.2.0).

**Binding Figma : `kind: "NONE"`** pour cette itération. Le master canvas du logo n'a PAS de variante Taille (les usages sont des instances redimensionnées), et 015 est Figma-lecture-seule (FR-010) : déclarer un VARIANT que le canvas n'héberge pas ferait mentir le contrat et mettrait l'axe canvas au rouge. `NONE` est le mécanisme déclaré du schéma pour « code-only par limite de fidélité assumée » (`parity/diff.ts:352-354` : skipped, pas BEHIND ; précédent : `ds.hero.backgroundUrl`). La note du prop pointe 016 : quand le chantier canvas ajoutera la variante au master, le binding sera promu VARIANT.

**Mécanique de mise à l'échelle des vecteurs — le seul lift moteur de ce travail.** Le logo est fait de deux parts `vectorAsset` à géométrie figée en px (`.Marque svg { width: 25.96px; … }`, positions absolues `left: 34.33px`) : une taille de root par variante ne les ferait PAS suivre. Décision : **lift d'émetteur** — quand le root d'un contrat porte une taille pilotée par référence interpolée, les parts `vectorAsset` émettent leur géométrie en **pourcentages du root intrinsèque**, calculés à la compilation (25.96/180 → `14.4238…%`), positions comprises (le root généré est déjà `position: relative`). Déterministe, octet-stable, zéro token supplémentaire, s'applique à toute taille future. Discipline Claims Rule : fixture d'eval AVANT la revendication (le CSS généré du logo rend proportionnel pour chaque valeur de `taille`). **Vérification préalable from-dump** : relever les deux tailles d'usage dans les dumps et vérifier qu'elles sont bien des homothéties de 180×34 — si l'usage header n'est pas proportionnel, la décision est re-posée avec le relevé en main (rien n'est supposé).

**Alternatives rejetées.** (a) Tokens par variante sur chaque champ des vecteurs (width/height/left/top ×2 parts ×2 variantes = 8+ tokens) — rejeté : prolifération, et `left`/`top` ne sont pas des canaux routés pour des parts non-overlay ; (b) `transform: scale()` via `stylesWhen` — rejeté : la boîte de layout ne suit pas le scale, `transform-origin` absent de `STYLES_WHEN_ALLOWED` ; (c) binding VARIANT immédiat + acquittement baseline — rejeté : déclarerait au contrat une capacité canvas inexistante (contraire à §V honnêteté).

## D5 — Les 2 dégradés du hero : littéraux nommés, avec un lift additif du canal `background-image`

**Constat docs-first qui corrige le brief.** La note parquée disait « zéro code moteur ». La description du contrat hero (v1.3.0, datée, la plus précise) dit le contraire, canal par canal : « Gradients are expressible in principle (§a.3: `tokens['background-image']` is parsed into a native GRADIENT_LINEAR) but that channel resolves ONLY through a DTCG token reference, and the Piqueray foundation defines no gradient token; **`literals` refuses the channel by name** (`background-image` is not in `LITERAL_CHANNELS`) and its value grammar admits no gradient syntax. » Le document fait foi sur l'inférence — et sur le brief.

**Décision.** Petit lift **additif** (Principe VI) : ajouter `background-image` à `LITERAL_CHANNELS` avec une grammaire bornée **propre au canal** (`linear-gradient(...)` uniquement — la grammaire générale `LITERAL_VALUE_RE` ne bouge pas ; le refus par nom reste pour radial/conic) ; router le canal dans `emit-react`/`emit-html`/`emit-react-inline` (déclaration `background-image` telle quelle) et dans `emit-figma-script` par le chemin `parseCssGradient` → `GRADIENT_LINEAR` **déjà écrit** pour la branche tokens (core/emit-figma-script.ts:807-… ; c'est le sens réel de « linear-gradient CARRY-BOTH depuis v15 »). Puis écrire les deux valeurs relevées dans le contrat hero, aux parts relevées par le dump :
- root, fills[2] : `linear-gradient(to top, rgba(0,0,0,0) 75%, rgba(0,0,0,0.5) 100%)`
- Titres, fills[0] : `linear-gradient(to bottom, rgba(0,0,0,0) 0%, rgba(0,0,0,0.5) 60%)`

Ces deux entrées **amorcent le registre des littéraux nommés** (D6) — c'est la décision de /clarify, non re-discutée ici. `docs/02-contract-spec.md` est bumpé avec le canal (Principe VI). Ordre Claims Rule : fixture d'eval (le littéral gradient rend sur les 4 surfaces ; une grammaire hors borne refuse par nom) avant toute phrase de capacité. Re-pins ×3 (les mêmes trois commandes que D1, dans le lot de la phase — il y en a un par phase qui touche émetteurs, contrats ou tokens, pas un seul pour toute la feature).

**Conséquence mesurée d'avance.** Les deux voiles pèsent 28,07 % des pixels du master hero (mesuré, description du contrat) — la ligne hero (27,83 %, cause `image-boundary`, reçu `org-hero-image`) va bouger fortement : c'est une **réparation attribuée** (FR-012), re-triée au registre avec un reçu re-testé (le résiduel attendu redevient le plan photo/rendu).

**Alternatives rejetées.** (a) Minter 2 tokens `gradient.hero.*` (chemin tokens déjà câblé, littéralement zéro code moteur) — rejeté : la clarification a tranché « littéral nommé, canal sans vocabulaire » ; un token à usage unique fabriquerait un faux vocabulaire, exactement ce que la liste fermée existe pour éviter. (b) `DECLARED_CHANNELS` — rejeté : `declared` porte des canaux de comportement/mot-clé, et l'inventaire des valeurs en dur (`inventoryLiterals`, D12 de 013) balaye `literals`/`literalsByProp`, pas `declared` : un dégradé en `declared` serait invisible à l'instrument d'inventaire qui fonde le contrôle FR-001.

## D6 — Le registre des littéraux nommés : `contracts/named-literals.registry.json`

**Décision.** Une **liste fermée, machine-lisible, une seule source**, au format JSON commité : `contracts/named-literals.registry.json` (précédent du répertoire : `contracts/icons.registry.json` — les documents gouvernés non-contrats vivent là ; les chargeurs de contrats filtrent sur le suffixe `.contract.json`, aucun risque de collision). Une entrée par exception, **à l'entrée près** : `{ contractId, pointer (JSON Pointer RFC 6901 vers le canal exact), channel, value (épinglée), reason, decidedOn, receiptId }`. Amorcée aux 2 dégradés du hero. Toute addition passe par une décision consignée avec reçu — le contrôle refuse une entrée sans `reason`/`receiptId`/`decidedOn`.

**La valeur est épinglée** dans l'entrée : c'est ce qui rend le littéral nommé *surveillé* et pas seulement recensé — si le contrat et le registre divergent (quelqu'un change le dégradé d'un côté), la porte géométrie (D7) le signale. Nommé ≠ invisible, ET nommé = comparé.

**Alternatives rejetées.** (a) `parity/baseline.json` — rejeté : les acquittements baseline sont des tolérances de dérive en cours, pas un vocabulaire permanent de décisions ; (b) un champ dans chaque contrat — rejeté par la clarification (« une seule source, lisible par le contrôle ») ; (c) un critère par type de canal — rejeté par la clarification (liste fermée à l'entrée près).

## D8 — Le comptage v2 de la porte de mesure : `aggregateOf` (1:N) + unité « travail à faire »

**Constat.** `evaluateMeasureGate` (extract/figma/measure-gate/gate.ts:321-334) compte aujourd'hui : +1 par ligne divergente à cause valide, +1 par entrée DW re-classée sauf si son `dedupeKey` (mappé depuis `sameDefectAs`, run.ts:257-262) pointe une ligne déjà comptée — le dédoublonnage 1:1 de §4 bis. Le 7 d'ouverture se décompose exactement : 3 entrées DW sans dedupeKey (DW-001, DW-004, DW-005) + 3 lignes d'organismes (`texte-seo` 1,84 %, `footer` 1,04 %, `coordonnees` 0,52 %) + 1 ligne de parité visuelle (`section-header :: Avec CTA` 8,78 %, règle TRIAGE classe `contract-geometry`, reçu `pv-section-header-avec-cta`). La ligne footer et les 3 faits DW décrivent le même chantier : 1 + 3 = 4 comptés pour 3 travaux — le N+1 que la clarification refuse.

**Décision.** Étendre gate.ts + run.ts, fixture d'abord (`evals/fixtures/measure-gate-policy-check.ts` est la fixture existante à enrichir) :
1. `MeasuredLine.aggregateOf?: string[]` — mappé depuis un nouveau champ `aggregateOf` des `organismLines` de `causes.json`. Une ligne qui agrège N faits contribue **0** au comptage ; ses N faits comptent chacun 1. (L'inverse exact du `dedupeKey` existant, qui supprime le FAIT quand la LIGNE compte — les deux directions coexistent, jamais sur la même paire.)
2. `ReclassifiedDwEntry.resolvedBy` remonte dans le comptage : une entrée avec `resolvedBy` non nul n'est **plus un travail à faire** — elle sort de `byCause` (elle reste dans le registre et sous C4). C'est la sémantique « unité = travail à faire » de FR-006 appliquée aux deux populations.
3. `causes.json` : la ligne `footer/footer-master-defaults` reçoit `aggregateOf: ["DW-001", "DW-004", "DW-005"]` (dwIds, cohérents avec `sameDefectAs.kind: "deferredWork"`).

**Relevé d'ouverture re-lu après modélisation** (publié par `npm run measure:gate`, jamais recopié) : attendu 6 pour `contract-geometry` (3 faits footer + texte-seo + coordonnees + Avec-CTA) et 0 pour `instrument` (DW-006 est `resolvedBy: "014"`) — le compte vif fait foi si le calcul me contredit. La clôture : DW-001/004/005 passent `resolvedBy: "015"`, les lignes re-mesurées repassent sous 0 de score brut → `contract-geometry` = 0, porte PASS (SC-005, FR-013). La sémantique v2 est documentée dans `specs/015-…/contracts/measure-gate-counting-v2.md` (le doc d'interface de 014 reste daté, non réécrit).

## D9 — FR-005, la boucle prouvée des deux côtés : deux cas d'eval C3

**Décision.** Deux nouveaux cas dans la famille C3-detection d'`evals/run.ts` (≈20 cas existants, patron établi : muter le scratch, affirmer la détection nommée) :
