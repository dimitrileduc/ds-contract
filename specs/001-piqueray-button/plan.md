# Implementation Plan: Reconversion Piqueray — preuve Figma → code sur le Button

**Branch**: `001-piqueray-button` | **Date**: 2026-07-22 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-piqueray-button/spec.md`

## Summary

Reconvert the repository **in place** from the 51-component demo design system to
**Piqueray**, proving the "Figma → contract → code, provably faithful" chain end-to-end on a
single component: the **Button**. The load-bearing sequence is **tokens-first**: replace the
multi-brand / dual-theme demo tokens with a single-mode Piqueray foundation (14 Figma
variables + 8 Montserrat typography styles) modelled on the existing tiered architecture
(primitives → semantic aliases); then extract a **Button contract** from a timestamped Figma
**dump** (fileKey + node anchors), hand-review and approve it, **generate** its React
component + Storybook story deterministically, and turn the repo's existing arsenal green on
it: byte-identical ×2 (determinism), code↔contract (parity), contract↔Figma (drift listed in
plain language), and render↔Figma (visual parity, within the repo's existing masked-diff
tolerance). Each step is human-approved and recorded as **one git commit per step**.

Technical approach is **subtractive + additive within existing mechanisms**: generation,
catalog, dashboard, Storybook, and parity are all **glob-driven over `contracts/`**, so
removing all 51 demo contracts + regenerating auto-shrinks every surface. Only three surfaces are
**hardcoded** and must be edited by hand: the eval suite's demo-coupled cases
(`evals/run.ts`, resolved by the documented hybrid rule), the golden manifest
(`evals/golden.json`, regenerated by `npm run golden:update`), and the visual-parity subject
list (`extract/figma/visual-parity/subjects.ts`, repointed to the Piqueray file). Two small
**additive-optional schema fields** carry provenance the spec requires (dump timestamp;
authored-vs-extracted a11y marker), per Principle VI.

## Technical Context

**Language/Version**: TypeScript 5.x, Node ≥ 20, ESM (run via `tsx`)
**Primary Dependencies**: Zod (`@ds-contracts/schema`), React 18 + CSS Modules (the `react`
emitter — the only one wired into `npm run generate`), Vite (dashboard/playground/lib build),
Storybook `@storybook/react-vite`, `playwright-core` (visual parity, real Chromium), Figma
Plugin API (canvas emit target; faithful Node-VM mock for headless gates)
**Storage**: JSON on disk — `contracts/*.contract.json` (source of truth), DTCG
`tokens/*.tokens.json`, generated `catalog/` shards, byte-pinned `evals/golden.json`, Figma
dump fixtures under `extract/figma/fixtures/`
**Testing**: `evals/run.ts` deterministic suite (families C1 determinism, C2 refusal, C3
detection, C4 convergence, C5 extraction, C6 theming, C7 cli, C8 journey — live `N/N` is
authoritative, ~146); `npm run parity` (three-way differ); `deterministic-roundtrip.mjs`;
`plugin:check`; `core-browser-check.mjs`; `extract:figma:visual` (Chromium)
**Target Platform**: Node CLI + browser-pure `core/` engine + generated React library +
Figma plugin
**Project Type**: Generator / candidate reference implementation (single repo, npm workspaces)
**Performance Goals**: Byte-identical regeneration across two runs (the product guarantee);
contract-validated build; visual masked-diff within the **existing** `THRESHOLD_PCT = 2.0%`
gate (no new threshold introduced)
**Constraints**: Zero `node:*` in `core/`'s module graph; **no AI in the contract→surface
path**; **no invented token values** (every Piqueray value comes from the dump); schema grows
by **optional fields only**; degradation named, never silent
**Scale/Scope**: 51 demo contracts + multi-brand (default/aurora) + dual-theme (light/dark)
tokens → **1 Button contract + Piqueray mono-theme foundation** (14 variables: 12 colors +
NavState + Opacity; 8 Montserrat styles; single mode). Eval suite re-pointed via the hybrid
rule (count may change, stays green). No NEEDS CLARIFICATION remain — the spec resolved 4
clarifications; research resolved the rest against real mechanisms. The only external input
is the Piqueray Figma dump (fileKey + variable values + typography), captured as the first
sub-step of extraction and **never invented in planning**.

- [x] **III. Contract is the SSoT** — Button is a single versioned `contracts/*.contract.json`;

      `contracts/contract.schema.json` are only ever regenerated. Removal deletes then

      edited by hand are all **source**: `tokens/`, `evals/run.ts`, `subjects.ts`, the schema.
      ✅
- [x] **V. Honesty** — Extraction marks inferred/unbound values and names what it can see but
      not read; the authored a11y baseline is **explicitly marked** authored-not-extracted

      removed eval cases are **named** under the hybrid rule (FR-002). ✅
- [x] **VI. Additive evolution** — Two schema changes, both **optional additive fields**

      `docs/02-contract-spec.md` is bumped with them. The Piqueray Button contract is authored

- [x] **VII. Engine integrity** — `core/` stays browser-pure
      (`core-browser-check.mjs`). If the visual gate surfaces a live-only defect (as the SVG
      bug once did), the fix is two-part: fix the emitter **and** teach the mock/gate to catch

**Structure Decision**: Single existing repo, reused **in place** (FR-001 — no separate repo,
no fallback). The reconversion is expressed almost entirely through the repo's existing
glob-driven generation: delete contracts → regenerate → every downstream surface follows. The
work concentrates in four hand-authored sources — `tokens/` (the Piqueray foundation),
`contracts/button.contract.json` (authored from the dump), the schema (+2 optional fields),
and the three hardcoded lists (`evals/run.ts`, `evals/golden.json` via regen,
`visual-parity/subjects.ts`). This keeps the change surface honest and small, and lets each
of the five user-story stages land as an independently-testable, human-approved commit.
