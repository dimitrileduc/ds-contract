## Défaut d'instrument révélé par ce lot — et corrigé

Le mint de **284,4** a fait apparaître un **faux mismatch permanent** :

```
[figma-tokens MISMATCH] Primitives/size/reassurances/carte-cinq-cartes [Value]
  tokens/ says 284.4, Figma says 284.3999938964844
```

**Cause** : Figma stocke les variables `FLOAT` en **simple précision**. Écrire 284,4 rend
284.3999938964844. `parity/diff.ts` comparait les valeurs par leur **chaîne** — aucune
ré-exécution n'aurait pu éteindre ce finding : le différentiel réclamait la correction
d'une valeur déjà correcte.

**Correction** : `memeValeur()` compare les nombres via `Math.fround`, c'est-à-dire ce
que `tokens/` **veut dire** contre ce que Figma **peut stocker**. Ce n'est pas une
tolérance mais l'arithmétique exacte du stockage. La détection reste stricte :

| | |
|---|---|
| `fround(284,4)` vs `284.3999938964844` | **égales** ✓ |
| `fround(364)` vs `fround(363,5)` | différentes ✓ |
| `fround(284,4)` vs `fround(284,5)` | différentes ✓ |
| `fround(364)` vs `fround(999)` (sentinelle) | différentes ✓ |

**Pourquoi le défaut dormait** : tous les tokens décimaux de la fondation étaient des
`.5` (363.5, 339.5), que float32 tient exactement. `284,4` est **le premier** à ne pas
l'être.

**Précédent qui fait jurisprudence** : `parity/extract-figma.plugin.js` porte le même
correctif pour l'alpha des couleurs — *« the instrument inventing drift that does not
exist »*. Quand l'instrument invente une dérive, c'est l'instrument qu'on répare.

## Addendum T030 (2026-08-06) — la preuve côté React : **delta 0**

**Verdict : ✅ la prémisse de la décision owner est vérifiée sur la surface React
livrée.** Le rendu React des cartes est indistinguable avant/après la décision — pas
« visuellement proche » : les captures avant/après sont **byte-identiques** (mêmes
sha256), et chaque largeur mesurée est strictement égale dans les deux états.

### Ce que la décision supposait

La décision du 2026-08-05 (« on ajuste les cartes, jamais le conteneur ni les gaps »)
reposait sur une prémisse côté code : la surface React livrée rendait **déjà** les
cartes à 363,5 px, parce que le conteneur contraint force le flex à absorber le
débordement (`4×364 + 96 = 1552 > 1550`, déficit de 2 px réparti sur 4 basis égales →
−0,5 px chacune). Fixer `size.carte.root` à 363,5 ne devait donc **rien** changer au
rendu React. T030 mesure cette prémisse au lieu de la croire ; un delta non nul aurait
suspendu la suite.

### Méthode — un rendu navigateur de la vraie surface livrée, pas `emit-html`

- **Ce qui est rendu** : `src/components/Reassurances` + `src/components/Carte` +
  `src/styles/tokens.css` de HEAD, **non modifiés**, compilés par le Vite du dépôt
  (8.1.3) et rendus par le React du dépôt — montés par un point d'entrée minimal
  (`.page-parity/dw002-react-rig/` : `index.html` + `main.tsx` reprenant les items du
  sample de la story générée, + `mesure.mts` ; dossier **gitignoré**, jamais commité).
  **L'instrument de parité visuelle (`emit-html`, limite DW-014-002) n'a PAS servi** —
  cette limite ne s'applique donc pas à la présente mesure.
- **Navigateur** : Google Chrome for Testing **151.0.7922.34**, l'exécutable épinglé du
  cache Playwright (`chromium-1234`), résolu par `chromiumExecutable()` de l'instrument
  du dépôt (`extract/figma/visual-parity/render.ts`). Viewport 1728×1200,
  `deviceScaleFactor: 1`, capture `fullPage` clippée sur le bloc `items` (clip figé,
  identique pour les deux états).
- **L'état AVANT sans checkout** : reproduit en surchargeant
  `--size-carte-root: 364px` sur `:root` de la page rendue. **Équivalence prouvée par
  git, pas supposée** : entre `1b9d531~1` et `1b9d531` (le lot), le SEUL changement

### Ce que la mesure montre en plus

- **La prémisse, confirmée par deux chemins** : avant, le moteur rend 363,5 par
  shrink (1552 → 1550) ; après, 363,5 par largeur exacte (4×363,5+96 = 1550 pile,
  aucun shrink). Même valeur, deux mécanismes — mesurés tous les deux.
- **Le débordement Figma n'a jamais existé côté React** : la 1ʳᵉ carte est à x = 0 du
  conteneur dans les deux états (au canvas elle était à x = 39 pour un frame à 40).
  Le flex absorbe, Figma laisse déborder — la différence de moteur que DW-002
  documentait est ici visible dans les chiffres.
- **Cinq cartes : le React converge vers le token minté sans le consommer.**
  `--size-reassurances-carte-cinq-cartes` (284,4) n'est branché sur aucun module CSS de
  `src/` — côté React la largeur 5-cartes émerge de la seule contrainte flex : mesuré
  `[284.40625, 284.390625, 284.40625, 284.390625, 284.40625]` (le moteur répartit en
  1/64 px : 3×18202 + 2×18201 unités = 1422 px exactement, **moyenne 284,4 pile**),
  identique dans les deux états. La valeur figée au canvas et le comportement flex React
  atterrissent sur le même nombre — mesuré, pas déduit.

### Limites nommées

1. **Le canal Storybook livré ne démarre pas sur HEAD** — c'est la raison d'être du
   rig : les stories **générées** `Footer.stories.tsx` (27:15) et
   `FooterColumn.stories.tsx` (28:11) portent des **U+2028 bruts** dans des littéraux
   (4 occurrences dans Footer) et l'indexeur refuse (« Unterminated string constant »).
   Famille du défaut U+2028 déjà connue du dépôt ; défaut préexistant, hors périmètre
   T030 — consigné, pas réparé.
2. **La story livrée ne rend pas le cas 5 cartes** : `Disposition5Cartes` hérite des
   items du meta (4). Le rig passe 5 items, le 5ᵉ étant une copie du 4ᵉ — sans effet
   sur la géométrie : la largeur des cartes est pilotée par `width`/flex, pas par le
   contenu (vérifié : aucun cas n'est bloqué par un `min-content`).
3. Pas de `@font-face` dans le rig (police fallback système) — sans effet sur le
   delta : les deux états partagent la même page chargée, seule la variable change
   entre les deux mesures.
